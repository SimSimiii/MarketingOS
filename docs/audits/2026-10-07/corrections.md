## 3. Sécurité et comptes

- **SEC-01 :** les deux consoles passent à Next.js et eslint-config-next **16.3.8**, avec locks alignés, correctifs de Sharp/source-map-js et mises à jour transitives compatibles. La nouvelle passe a pris en compte les avis apparus depuis le contrôle du 7 octobre ; le correctif 16.3.6 seul n’était plus suffisant. La version corrigée est indiquée par [l’avis Next.js sur les caches Draft Mode](https://github.com/vercel/next.js/security/advisories/GHSA-3w37-wq28-93x7). Le résultat final npm est consigné dans les preuves de corrections ; il ne constitue pas un pentest.
- **SEC-02, partie applicative :** compteur partagé en DB, transaction atomique SQLite/PostgreSQL, 12 tentatives par identité normalisée et endpoint dans une fenêtre fixe de 5 minutes. Login/inscription produit et login admin sont couverts. Le refus 429 fournit `Retry-After` avant bcrypt et s’applique aux identités connues comme inconnues. Les clés sont des HMAC, les compteurs anciens sont purgés. Une attaque sur un compte ne bloque pas un autre compte ; les headers X-Forwarded-For ne permettent pas de changer la clé. Le login admin exécute aussi la vérification bcrypt pour une adresse inconnue. **La limitation par client/IP à l’entrée, les endpoints coûteux et l’accès privé du worker restent à configurer.**
- **SEC-03 :** défaut `/api`, proxy Next en développement et profil auth aligné sur la même origine. Les deux exemples d’environnement sont désormais livrables malgré le gitignore ; l’override local existant a été ramené à `/api`. Production : router `/api/*` sur le domaine de la console. Le parcours cookies réel reste à vérifier au navigateur.
- **SEC-04 :** logout vérifie la réponse et affiche un échec réseau/HTTP, puis navigue seulement après réussite. La sémantique du bearer copié après logout simple n’a pas été transformée en révocation immédiate par session.
- **SEC-07 :** les fixtures admin utilisent le moteur produit avec contraintes FK actives. Les tests couvrent la conservation des comptes/mouvements financiers. Réconciliation, permissions financières spécifiques et protection MFA/SSO restent à traiter.

La vérification Python a également trouvé des avis sur PyJWT 2.14.0 et pypdf 6.18.1. Les trois locks passent respectivement à **PyJWT 2.15.1** et **pypdf 6.19.0**, avec une borne minimale PyJWT 2.15.0 dans le manifeste ; les autres pins sont conservés ou alignés sur le lock de développement. Les mainteneurs documentent les correctifs [PyJWT](https://github.com/jpadilla/pyjwt/security/advisories/GHSA-42vr-xj54-vc7v) et [pypdf](https://github.com/py-pdf/pypdf/security/advisories/GHSA-w23x-9jrw-r45c). L’exposition exacte de chaque advisory n’est pas assimilée à une exploitation démontrée de MarketingOS. Le script [audit_python_locks.py](C:/Users/oussa/Desktop/Workspace/projects/MarketingOS/docs/audits/2026-10-07/audit_python_locks.py) consulte les avis de chaque version verrouillée publiés par PyPI et signale aussi les vérifications indisponibles ; il ne remplace pas un audit complet de supply chain.

Les locks finaux utilisent une résolution universelle avec uv : dépendances Linux conservées et packages Windows limités par marqueur. Le verrou Windows seul produisait un `pywin32` inconditionnel dans le worker et omettait `uvloop`, ce qui aurait cassé une installation Linux avec hashes. Ce défaut de génération est corrigé ; le daemon Docker local étant indisponible, l’image complète reste non construite dans cette session.

**Migration ajoutée : `b7a109c4e2f8`**, après `a4e92f6b17c0`, pour les compteurs d’authentification. Elle concerne la base partagée des deux APIs. Aucun upgrade de la base de développement n’a été effectué. Avant déploiement : sauvegarder, identifier la vraie révision, puis appliquer la chaîne. Ne pas stamper un ancien schéma directement au nouveau head. La montée/descente/remontée et la parité ont été vérifiées sur SQLite temporaire ; PostgreSQL reste à tester réellement.
