# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## Branch policy

Make all changes and commits on the branch that is currently checked out. Do not create
or switch branches, and do not create a separate worktree. This applies to every task,
including `optimize`, in both Codex and Claude Code. Only depart from this policy if the
user explicitly requests a different branch or worktree for that task.

## What this is

An email-copy generator: it reads a business's own material into a set of facts it is
allowed to claim, plans a campaign, writes each email, has every draft read cold by a model
that has never seen the brief, and rewrites what did not land. Backend is FastAPI +
SQLModel + SQLite; frontend is Next.js App Router. `README.md` explains *why* the
architecture is shaped this way and is worth reading before changing the pipeline — almost
every design decision in it was made against a measured failure.

## Commands

All backend commands run from `backend/`. On Windows call `.venv/Scripts/python.exe`
directly rather than activating the venv.

```bash
pip install -e ".[dev]" && cp .env.example .env && alembic upgrade head
```

```bash
uvicorn app.main:app --reload
```

```bash
.venv/Scripts/python.exe -m ruff check app tests
```

Lint `app tests`, not `.` — `alembic/versions/` is autogenerated and has never been
import-sorted, so linting the root reports ten `I001`s that are not yours. The clean baseline
is one pre-existing `SIM102` in `app/ai/openai_provider.py`. **Do not run `ruff format`**: the
repo is not format-clean (116 of 293 files would be rewritten), so it buries a real change in
an unrelated diff.

```bash
alembic revision --autogenerate -m "what changed"
```

The whole test suite is scripted-provider based — 785 tests, green, ~50 seconds, no quota
spent. Run it. `pytest-asyncio` is in strict mode, so an async test needs an explicit
`@pytest.mark.asyncio`.

```bash
.venv/Scripts/python.exe -m pytest tests -q
```

```bash
.venv/Scripts/python.exe -m pytest tests/marketing/test_gates.py::test_name -q
```

Frontend, from `frontend/`:

```bash
npm run dev
```

```bash
npm run lint && npx tsc --noEmit
```

Both are clean as of writing, so anything either one reports is yours.

There is no CI and no frontend typecheck script. Run the checks yourself before calling a
change done. `.Codex/launch.json` defines `backend` and `frontend` for the preview tools —
use those rather than starting servers by hand.

### Evaluation

`backend/app/evaluation/` holds two instruments, both run from `backend/`. **The billed ones
spend real subscription quota** — reach for the free ones first.

```bash
.venv/Scripts/python.exe -m app.evaluation.judge_bench --dry-run
```

```bash
.venv/Scripts/python.exe -m app.evaluation.runner --compare eval/before eval/after
```

Those two call nothing. The billed pair: `judge_bench --out eval/judges.txt` asks whether the
judges can tell good copy from deliberately damaged copy (~132 calls), and
`runner --preset balanced --out eval/after` runs whole campaigns end to end, duelling the
first email against a human-written one. Both take `--case` to run a single case.

## Architecture

### The run is a state machine, not an agent

`app/marketing/pipeline.py` fixes the order of work in code. No model call decides what
happens next — for a single channel the order follows from data dependencies. Every model
call in a run either distills knowledge, decides strategy, writes copy, or judges copy.
Routing, retries, thresholds, budgets and cancellation are ordinary Python.

Three phases: **knowledge** (chunk the corpus, compile six artifacts keyed by a fingerprint
of the material, so an unchanged corpus is never recompiled) → **strategy** (one Strategist
call turns request plus artifacts into a brief per email) → **craft** (write, gate, cold-read,
critique, rewrite, then read the whole sequence).

### Everything funnels through three choke points

- **`ModelSession`** (`app/runtime/model_session.py`) is the only thing that calls a model. It
  renders prompts from disk, counts tokens, types vendor failures as `ProviderError`, resends
  calls that failed in transport, and announces every call on the event bus.
- **`ExecutionEventEmitter.emit`** (`app/orchestration/event_emitter.py`) both persists an
  `ExecutionLog` row and publishes the identical payload to the SSE broker. Doing both in one
  call is what makes the live page and the replayed history agree by construction — never add
  a path that does one without the other.
- **`CampaignOrchestrator`** (`app/orchestration/campaign_orchestrator.py`) is a persistence
  adapter, not a decision-maker. It hands the request to the pipeline, watches through an
  observer, and writes rows. Keep decisions out of it.

### Tiers, models, and who bills

Roles ask for a `ModelTier` (`fast` / `balanced` / `deep`), never a model name.
`app/ai/models.py` is the catalog both `ModelRouter` and the UI picker read, so the dropdown
can never offer a model the router does not know; `app/ai/roles.py` is the presentation half
(role ids, blurbs, which capabilities each role passes).

Both providers bill a *subscription*, not an API balance: `ClaudeProvider` drives the Codex
Code CLI, `OpenAIProvider` drives `codex exec`. In each, `_clean_env()` strips the vendor's
API key from the subprocess environment — with the key visible, the CLI silently switches to
API-key billing and charges a card. That filter is the first thing each provider's suite
tests; do not weaken it, and do not put `ANTHROPIC_API_KEY` in `.env`.

### Checks that block are deterministic; judgment never blocks

`app/marketing/gates.py` reads every draft back and licenses each number, price, quotation and
URL against the Evidence Ledger or the user's own material. `clarity_gate` beside it blocks a
draft that never names the offering anywhere the reader is looking - the sign-off does not count,
because it answers who sent this rather than what this is. Comparisons are typography-blind
on purpose (a CMS makes apostrophes curly; a model quotes back in ASCII, and an exact
substring test silently drops correctly quoted proof). `app/marketing/substantiation.py` points
the same check the other way — did the email actually *spend* the evidence it was built on —
and `app/market/sameness.py` blocks a short closed list of argument frames every competitor
also uses. Taste never blocks: a cold reader can send a draft back for a rewrite, but only
code stops it shipping.

The one thing a cold reader *does* decide is comprehension. `BlindRead.understood` is whether
they could say what was being sold without guessing, and it is a veto rather than a term: a
draft the panel could not decode loses to one they could at any click estimate, and a click
estimate on an email nobody parsed is an answer to a different question. See
`EmailVersion.measured`, where it sits above `pull` and below the gates.

### Only `app/market/` may touch the open web

`ResearchTool` (web search, web fetch) is passed by market-intelligence roles and by nothing
that writes or judges copy. Pinning a market role to a GPT model is refused at save time,
because Codex has no `web_fetch` equivalent.

### Frontend

Pages are server components calling the API directly; mutations are small colocated
`"use client"` components. Everything scoped to a business lives under
`src/app/brands/[brandId]/` (knowledge, market, proof) — `/market` and
`/knowledge/base?brand=` redirect there for old bookmarks, and what remains at `/knowledge` is
sources attached to a one-off campaign. `src/lib/types.ts` mirrors the backend's Pydantic
schemas by hand, so a schema change means changing both. The execution page splits into a
stream hook, a pure fold (`lib/run-timeline.ts`) and a dumb component, so replayed history and
live events go through the same function. Theme is dark-only, violet accent, no toggle.

**This is Next.js 16, newer than training data.** Read the relevant guide in
`frontend/node_modules/next/dist/docs/` before writing Next-specific code — see
[frontend/AGENTS.md](frontend/AGENTS.md).

## Things that will bite you

- **Never run a real campaign to check a code change.** `tests/marketing/conftest.py`'s
  `RoleScriptedProvider` answers per *role* rather than per call position, so a test says "the
  cold reader hated this draft" and stays true however many calls the run makes around it.
  Spend a real model call only when the model's own behaviour is the question.
- **Per-role overrides take model names, not tier names.** `{"email_writer": "opus"}` is right;
  `{"email_writer": "deep"}` passes every scripted test and dies on the real CLI. Valid values
  are the catalog's: `haiku` / `sonnet` / `opus` / `fable5`, or a GPT slug.
- **Prompts are coupled to schemas and gates.** `backend/prompts/*.md` are Jinja templates
  rendered with `StrictUndefined`, so a variable the template names and the caller omits raises
  at render time. Field names in a prompt must match the Pydantic keys the response parses
  into, thresholds sit next to the gate that enforces them on purpose, and a literal `{{...}}`
  (a merge field, say) has to sit inside `{% raw %}`.
- **The dev database is not Alembic-managed.** `init_db()` runs `SQLModel.metadata.create_all`
  on every startup, so a local `marketingos.db` created that way has no `alembic_version` row.
  Run `alembic stamp head` before `alembic upgrade head`, or the first migration fails on
  tables that already exist.
- **`tests/conftest.py` must stay the first thing imported.** It sets `APP_ENV` and
  `DATABASE_URL` before any app module resolves settings; without it `TestClient(app)` runs the
  real lifespan against `marketingos.db`, and `reap_orphaned_executions()` kills whatever
  campaign was in flight.
- **Keep the API test engine file-backed.** `tests/api/conftest.py` deliberately avoids an
  in-memory `StaticPool`: those tests always have two sessions live at once (the request thread
  and the background campaign task), and one shared connection makes them one transaction. That
  was the entire cause of the suite's old flakiness.
- **Adding a model call to the loop means updating the forecast.** What a run will cost is
  shown before it is bought; `tests/marketing/test_forecast.py` executes the pipeline at every
  preset, counts the calls it made and asserts the forecast contained them.
- **The SSE broker and `ExecutionRegistry` are in-memory and process-local.** Correct for a
  single worker, and the first thing a multi-worker deployment would have to move to Redis.
- **Degrade, never deadlock.** Budgets, deadlines and cancellation are checked *between* steps,
  never mid-call. A failure that arrives with finished emails behind it is `degraded`, never
  `failed`.

## Constraints on what to propose

From [docs/external-review-brief.md](docs/external-review-brief.md): there are no users and no
real send data, so anything whose first step is "collect telemetry" or "calibrate on the
operator" is dead on arrival. Every model call costs real quota from a personal subscription,
so a change that increases spend has to say what it buys. Solo developer — implementation
effort is the scarcest resource after quota. No fine-tuning budget.
