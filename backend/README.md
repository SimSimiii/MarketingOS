# MarketingOS Backend

FastAPI + SQLModel + Alembic. Python 3.12+ (targets 3.13; nothing here is 3.12-specific).

## Setup

```bash
python -m venv .venv
.venv/Scripts/activate        # .venv/bin/activate on macOS/Linux
pip install -e ".[dev]"
cp .env.example .env
alembic upgrade head
uvicorn app.main:app --reload
```

API docs at http://localhost:8000/docs once running.

## How a campaign runs

Three phases, orchestrated in code (`app/marketing/pipeline.py`). There is no LLM
deciding what runs next — for a single channel the order is fixed by data dependencies,
and every model call in a run either distills knowledge, decides strategy, writes copy,
or judges copy.

**Phase 0 — knowledge.** Everything the user provided is chunked and made searchable
(`app/knowledge/corpus.py`), then the `KnowledgeCompiler` distills it into six artifacts:
Business Profile, Offer Sheet, **Evidence Ledger**, Voice Profile, Audience Model, Gap
Report. They belong to the *brand*, not the campaign, and are keyed by a fingerprint of
the material — an unchanged corpus is never recompiled, so the second campaign for a
business starts from everything the first one learned.

**Phase 1 — strategy.** The deliverable contract ("5 emails") is parsed out of the
request in code, then one strong-model `Strategist` call turns request + artifacts into a
Campaign Brief: the reader, the promise, the arc, and one Email Brief per email naming
the single idea it owns, the evidence ids it spends, and the objection it kills.

**Phase 2 — craft.** Per email: the **Writer** drafts it, deterministic **gates** check
it, a **Blind Reader** who has never seen the brief reads it cold, a **Conversion Critic**
turns that reading into line-level edits, and the writer revises. The version that
actually scored better is the one that ships. Then the whole set is read as a sequence.

`GET /api/executions/{id}/assets` returns the copy-pasteable results.

## Why claims in the copy are checkable

Telling a copywriter "never invent a statistic" is an instruction, and instructions are
followed approximately. So every entry in the Evidence Ledger carries the verbatim source
text that supports it, and `app/marketing/gates.py::evidence_gate` reads every finished
draft back: every quantified claim, quoted passage and URL must be licensed by the ledger
or by the user's own material, or the draft bounces back to the writer with the exact
offending line. No model is asked whether the copy is honest.

The compiler is held to the same standard: an evidence entry whose quote cannot be found
in the source document is dropped before it is ever stored, because a hallucinated
testimonial would otherwise poison every campaign written afterwards.

The other gates are the same shape — free, deterministic, phrased as the fix: structure
(`email_copy.py`), unfilled placeholders (with a configurable merge-field vocabulary, so
`{{first_name}}` is personalization rather than an error), stock phrasing, spam-filter
vocabulary, and cross-email repetition.

## The five roles

| Role | Model tier | Sees | Blind to |
|---|---|---|---|
| Knowledge Compiler | balanced (+deep for audience) | the corpus | the campaign |
| Strategist | deep | request, all artifacts, prior campaign report | raw corpus (retrieval only) |
| Email Writer | deep | its brief, voice, ledger, prior emails verbatim | who will judge it |
| Blind Reader | balanced | one rendered email + a persona | **everything else — by design** |
| Conversion Critic | deep | email, brief, ledger, reader report, gates | the writer's reasoning |

The "blind to" column is the architecture. A role earns its own context when its
ignorance or its independence is load-bearing — the blind reader exists *because* of what
it is not given. Splitting by job title instead is what produced the old four-agent
analysis chain, which is now one Strategist.

Roles ask for a `ModelTier` (`fast` / `balanced` / `deep`), never a model — see
`app/ai/model_router.py`. A campaign or policy preset can override any role by id, or all
of them with `"*"`.

## Watching a run happen

A campaign takes minutes and spends most of them inside single `generate()` calls, so the
run narrates itself. Every notable moment — a phase starting, a role taking a turn, a
prompt leaving for the model, gate results, a cold reader's verdict, an email landing —
goes through one funnel, `ExecutionEventEmitter.emit`, which **both** writes an
`ExecutionLog` row and publishes the identical payload to the SSE broker. Persisting and
broadcasting in the same call is deliberate: the live stream and the history a reloaded
page replays can then never disagree.

The unit of the timeline is one **role turn** — one writer draft, one cold read, one
critique. That is finer-grained than the old director's steps and more honest, because it
is also the unit that costs money.

- `GET /api/executions/{id}/stream` — SSE, resumable. Each event is sent with an `id:`; a
  client reconnecting sends `Last-Event-ID` (or `?after_event_id=`) and the broker replays
  what it missed from a per-execution ring buffer.
- `GET /api/executions/{id}/timeline` — the same payloads replayed from the database, plus
  the `last_event_id` to resume the stream from.
- `GET /api/executions/{id}/logs?agent_id=&include_debug=` — one run's lines, optionally
  narrowed to a single role's lane.
- `GET /api/executions/running` — every run in flight, for the live dashboard.

The broker is in-memory and process-local, like `ExecutionRegistry`: correct for the MVP's
single-worker deployment, and the one thing a multi-worker deployment would have to move
to Redis pub/sub (or similar) first.

## Brands, and where knowledge lives

A `Brand` is a business the system knows about. Attach a campaign to one (`brand_id`) and
its compiled knowledge is shared by every campaign for that brand; leave it off and the
campaign compiles its own and keeps it, which is right for a one-off.

- `POST /api/brands` — register a business.
- `GET /api/brands/{id}/knowledge` — what the system currently knows, including what it
  could *not* establish and what that costs the copy.
- `POST /api/knowledge` with `brand_id` — file material under the business rather than one
  campaign. A website URL is **crawled** by default (`crawl: true`, `max_pages`), not
  fetched: prices live on /pricing and proof lives on /customers, and a campaign grounded
  only in a hero section has nothing specific to say.

## Extending to another channel

The knowledge and strategy phases are channel-agnostic; only the craft loop is
email-shaped. A new channel is a *channel pack*: a format contract (the equivalent of
`email_copy.py`), channel-specific gates, a writer prompt, and a reader persona. It reuses
phases 0 and 1 wholesale.

## Adding an AI provider

Implement `AIProvider` (see `app/ai/base.py`) in a new module, then add a branch in
`app/ai/factory.py::get_ai_provider`. Nothing outside `app/ai/` imports a vendor SDK, and
every model call in the system goes through `ModelSession` (`app/runtime/model_session.py`)
— which is also where vendor exceptions become typed `ProviderError`s, tokens are counted,
and each call announces itself on the event bus.
